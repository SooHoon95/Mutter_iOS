# Lessons — 자기 교정 누적

### 2026-10-13 — "가치 전달"을 문장으로 설명하는 릴스로 해석했다 — 원한 건 나이키식 브랜드 필름
- 상황: 훅 릴스 4편(A·C·D·E)을 전부 자막 문장 + 일러스트 카드로 설계했다. 사용자: "이런 감각적인 마케팅 홍보영상 뽑고 싶다고". 원하는 기준은 나이키 — 기능·효과를 말하지 않고, "그걸 했을 때의 내 모습"을 상상하게 하는 영상.
- 교정: 화면의 주인공은 문장이 아니라 사람과 순간(표정·공기·소리). 카피는 끝에 한 줄. 실사 질감이 필요하면 텍스트 모션으로 대체하지 말고 생성 영상(Veo/Kling/Seedance) 경로를 먼저 연다.
- 규칙: **브랜드 영상은 "무엇을 말할까"가 아니라 "보는 사람이 어떤 장면 속 자기를 상상하나"로 설계한다.** 설명 자막·기능 언급 0, 슬로건 1줄. 도구 한계(실사 소스 없음)는 사용자에게 바로 말하고 대체 경로를 고르게 한다.

### 2026-10-11 — 규칙만 지킨 "안전한" 릴스가 볼 것 없는 텍스트 슬라이드가 됐다
- 상황: 첫 줄 릴스를 앱 UI·폰·손·클립 전부 금지하고 Pillow로 아이보리 배경 위 작은 명조 문장 5장 + 크로스페이드로 만들었다. 사용자: "어제 만든 gif 진짜 구리고 별로야".
- 1차 교정안(오답): "앱 화면을 주인공으로" 제안 → 사용자: "앱 화면이 중요한 게 아니라, 어떤 가치를 전달해서 불특정 다수가 쓰고 싶게 만드는 게 목적. 후킹을 해야지".
- 교정: 릴스의 주인공은 기능·UI가 아니라 **감정과 가치**(받는 순간의 울림, 말로 못 한 마음)다. 첫 1초 훅 → 공감 장면 → 가치 → 제품은 마지막에 짧게.
- 규칙: **마케팅 영상은 "무엇을 보여줄까"(소재)보다 "보는 사람이 왜 멈추고 왜 원하게 되나"(훅·가치)를 먼저 정한다.** 렌더 전 콘택트 시트로 "첫 프레임에서 스크롤이 멈추나, 끝나고 누군가에게 보내고 싶어지나"를 자가 판정한다. 제약(저작권·과장 금지)이 훅을 죽이면 제약 안에서 다른 감정 장치를 찾는다.

### 2026-10-11 — 인코더 한 경로가 막힌 것을 영상 제작 전체의 끝으로 취급했다
- 상황: native FFmpeg와 Terminal 시작이 실패하자 GIF만 만들고 MP4 렌더를 사용자에게 넘긴 채 턴을 끝냈다. 사용자: “하던거 계속 해 영상 어찌된거야”.
- 교정: 실제 MP4 미완료를 확인하고, 허용된 브라우저 WebCodecs 등 독립 인코딩 경로를 검토해 이어간다.
- 규칙: 실행 도구 한 경로의 실패와 요청 산출물의 불가능을 구분한다. 사용자에게 수동 실행을 넘기기 전 허용된 독립 제작 경로를 확인하고, 완료/부분 시안/미완료를 명확히 보고한다. 잠금·권한 거부를 우회하지 않고 별도의 승인된 도구를 사용한다.

사용자 교정이 발생할 때마다 최신 항목을 위로 추가한다. 포맷·아카이브 규칙은 `mutter-harness-ops`.

> 2026-10-08 정리: 1개월 이상 지난 항목은 `tasks/lessons-archive.md`로 이동. 오래 쓸 기술 규칙은 스킬로 흡수했다 — 빌드·에셋·일괄 치환(`mutter-conventions`), DI·모듈명·웹 에셋 경로(`mutter-architecture`), `.task(id:)`·명령형 뷰 `.id()`·재생 의도·`@Observable` 혼용(`mutter-swiftui`).

### 2026-10-05 — 백그라운드 작업을 "기다리는 중"이라고만 하고 손을 놓았다 — 기다림은 작업이 아니다
- 상황: 주간 루프 1회차가 끝났는데도 "완료 알림을 기다립니다"로 턴을 끝냈다. 사용자: "끝났는데 왜 계속 이어서 안 해". 실제로는 2회차 중복 검증·launchd 등록·eval·critic 등 독립적으로 바로 할 수 있는 일이 네 가지나 남아 있었다.
- 교정: 백그라운드 결과를 기다리는 동안 독립 작업(스케줄 등록, 문서, 다음 검증 준비)을 병렬로 진행하고, 상태 보고는 한 줄로 끝낸다.
- 규칙: **턴을 "기다린다"로 끝내기 전에 "지금 결과 없이도 할 수 있는 일이 있나"를 먼저 묻는다.** 있으면 그걸 한다. 정말 없을 때만 한 줄 상태 + 다음 단계 예고로 끝낸다. 긴 작업은 nohup으로 띄우고 결과 파일을 감시하는 패턴을 기본으로 쓴다.

### 2026-09-16 — TestFlight "업로드 성공"을 "테스터에게 보임"으로 보고했다 — 노출은 끝단(그룹 테스터)까지 확인해야 완료
- 상황: `fastlane beta`가 "Successfully uploaded"를 찍자 "처리 후 내부 테스터에 노출됩니다"라고 보고하고 넘어갔다. 2시간 뒤 사용자: "왜 안 올라오냐". 실제로는 (1) 1차 업로드가 1.0.3 트레인 마감(90186)으로 실패했고 재업로드했으며, (2) 재업로드 빌드는 VALID·규정준수 OK였지만 **내부 테스터 그룹에 사람이 0명**이라 아무에게도 배포되지 않았다. 업로드 성공과 "TestFlight 앱에 보임" 사이에 처리·규정준수·그룹 배정 세 단계가 있는데 하나도 확인하지 않았다.
- 교정: Fastfile에 `tf_status`(processingState·usesNonExemptEncryption·내부/외부 베타 상태·그룹별 테스터·팀 사용자)와 `tf_add_tester`(내부 그룹에 팀 사용자 추가) 레인을 만들어 확인·수정했다. 사용자 계정을 그룹에 넣은 뒤에야 빌드가 보인다.
- 규칙: **TestFlight 배포 요청은 `fastlane beta` 성공이 아니라 `fastlane tf_status`에서 `processing=VALID` + `internal=READY_FOR_BETA_TESTING` + 대상 그룹 테스터 ≥1을 확인한 뒤에 "올라갔다"고 보고한다.** 사용자가 기다리는 결과물은 "업로드 로그"가 아니라 "폰에서 보이는 빌드"다. 이미 스토어에 출시된 버전(트레인)에는 새 빌드를 못 올리므로 업로드 전에 MARKETING_VERSION이 라이브 버전보다 높은지 먼저 본다.
